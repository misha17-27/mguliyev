# Перенос на новый сайт

План рассчитан на cPanel с развёртыванием через Git Version Control.
Главное свойство: **на каждом шаге можно вернуться назад одним действием**.
Старый сайт и его база не удаляются и не перезаписываются — он просто
перестаёт быть тем, что отдаётся по адресу домена.

---

## Что меняется для посетителя

На старом сайте корень был английским, а переводы жили на `/ru/glavnaya/`
и `/az/glavnaya/`. На новом корень русский — так решено.

| Старый адрес | Новый адрес | Что произошло |
|---|---|---|
| `/` | `/` | адрес тот же, язык сменился с английского на русский |
| `/ru/glavnaya/`, `/ru/glavnaya-2/` | `/` | две копии русской главной свелись в одну |
| `/az/glavnaya/` | `/az/` | |
| `/about/` | `/en/o-studii/` | страница была английской |
| `/contact/` | `/en/kontakty/` | |
| `/projects/` | `/en/portfolio/` | |
| `/coming/`, `/test/` | `/` | служебные страницы, содержания нет |
| `/sitemap_index.xml`, `/page-sitemap.xml` | `/sitemap.xml` | |
| `/wp-admin`, `/wp-login.php`, `/xmlrpc.php` | 410 | на новом сайте их нет |

Все правила лежат в `public/.htaccess` и уже в репозитории.
Проверить после переключения — в пункте 6.

---

## 1. Резервная копия

До любых действий:

- полная копия файлов текущего сайта (cPanel → Backup → Download a Home Directory Backup);
- копия базы данных WordPress;
- запишите текущий document root домена — его видно в cPanel → Domains.
  Это та строка, к которой вы вернётесь при откате.

**Почту это не затрагивает.** Ящики, DNS-записи MX и пароли живут отдельно
от файлов сайта: смена document root на них не влияет.

---

## 2. Развёртывание

cPanel → Git Version Control → репозиторий → **Deploy HEAD Commit**.

По `.cpanel.yml` файлы лягут так:

```
~/public_html/   корень сайта
~/app/           шаблоны и данные, вне зоны доступа из сети
```

Основной домен в cPanel жёстко привязан к `public_html`, и сменить ему
document root из панели нельзя — поэтому корень кладётся прямо туда.
Страницы подключают шаблоны по пути `../app/`, и с такой раскладкой он
указывает ровно в `~/app`.

Ничего не удаляется: команды только копируют.

### Если cPanel пишет «The system cannot deploy»

Три требования в этом сообщении означают состояние **клона на сервере**,
а не репозитория на GitHub:

1. есть выгруженная ветка;
2. есть корректный `.cpanel.yml`;
3. на выгруженной ветке нет незакоммиченных изменений.

Самая частая причина — репозиторий на хостинге создавали, когда на GitHub
ещё не было ни одного коммита. Клон пустого репозитория остаётся без ветки
и без файлов, поэтому не выполняются сразу пункты 1 и 2.

Порядок действий:

1. Нажать **Update from Remote**. Это `git pull` на стороне сервера: он
   подтянет ветку `main` со всеми файлами, включая `.cpanel.yml`.
   После этого **Deploy HEAD Commit** становится доступен.
2. Если в ошибке сказано `"" is not a valid "branch"` — у клона нет ни одной
   ветки, и обновлением это не чинится: тянуть некуда. Нужно создать
   репозиторий заново (Git Version Control → Manage → Remove, затем Create
   тем же Clone URL). На GitHub при этом ничего не происходит.

3. Если при создании появляется `You cannot use the ... already contains
   files` — cPanel удалил запись, но файлы на диске оставил. Варианты:
   - **быстрый:** в поле Repository Path указать другую папку, например
     `repositories/mguliyev-site`. Старая останется лежать и мешать не будет;
     на `.cpanel.yml` это не влияет, он разворачивает в `$HOME/mguliyev-new`
     и к пути репозитория не привязан;
   - **аккуратный:** File Manager → зайти в `repositories/mguliyev` →
     удалить всё. Там лежит скрытая папка `.git`, а File Manager по умолчанию
     скрытые файлы не показывает: Settings → **Show Hidden Files (dotfiles)**,
     иначе папка останется «непустой» и ошибка повторится.

Проверить, что на GitHub всё на месте, можно не заходя на сервер: в корне
репозитория должны лежать `.cpanel.yml`, `public/`, `app/`.

## 3. Проверка на поддомене

Заведите `new.mguliyev.com` и укажите ему document root
`/home/mguliyev/mguliyev-new/public`.

Так новый сайт можно открыть и потрогать, пока на основном домене
работает старый.

**Требование к серверу:** PHP 7.4 и выше (разрабатывалось на 8.3).
Расширений и composer-зависимостей нет.

---

## 4. Что проверить до переключения

- [ ] открывается главная, в подвале виден логотип, стили загрузились
- [ ] работают все три языка: `/`, `/az/`, `/en/` — и переключатель между ними
- [ ] открываются все разделы: услуги и четыре подраздела, портфолио, о студии, цены, блог и три статьи, контакты
- [ ] на портфолио работает фильтр по отраслям, карточки открывают сайты клиентов
- [ ] в блоке вертикального видео проигрываются демо-ролики
- [ ] форма заявки отправляется (сейчас она **демонстрационная** — см. «Что ещё не готово»)
- [ ] `/app/` и `/_source/` снаружи недоступны — должны отдавать 403 или 404
- [ ] открывается `/sitemap.xml` и `/robots.txt`

### Если переключаете основной домен сразу, без поддомена

Так тоже можно — откат занимает столько же, сколько переключение. Разница
в том, что первыми проверяющими становятся посетители: поведение `.htaccess`
в Apache, отправка письма из формы и отдача `.mp4` на этом сервере
до переключения ни разу не запускались.

Чтобы окно было минутным:

1. **Update from Remote → Deploy HEAD Commit** — иначе на сервере не
   последняя версия.
2. **MultiPHP Manager**: у домена PHP 7.4 или выше. Ниже — белый экран.
3. Записать текущий document root. Это строка для отката.
4. Переключить и сразу прогнать проверку из пункта 6.

## 5. Переключение

cPanel → Domains → `mguliyev.com` → изменить document root на
`/home/mguliyev/mguliyev-new/public`.

Смена вступает в силу сразу, DNS не трогается, сертификат остаётся тот же.

**Откат:** вернуть прежний document root. Занимает столько же.

---

## 6. Сразу после переключения

Проверьте, что старые адреса уводят куда надо:

```bash
for u in / /az/ /en/ /portfolio/ /uslugi/veb-sayty/ /blog/ /kontakty/; do
  printf "%-24s %s\n" "$u" "$(curl -s -o /dev/null -w '%{http_code}' https://mguliyev.com$u)"
done
```

Все семь должны быть `200`. Затем редиректы и защита:

```bash
curl -sI https://mguliyev.com/about/        | grep -i '^location'   # /en/o-studii/
curl -sI https://mguliyev.com/ru/glavnaya/  | grep -i '^location'   # /
curl -sI https://mguliyev.com/projects/     | grep -i '^location'   # /en/portfolio/
curl -sI https://mguliyev.com/app/config.php | head -1              # 404
curl -sI https://mguliyev.com/images/demo/shot-1.mp4 | grep -i content-type  # video/mp4
curl -sI https://mguliyev.com/             | grep -i x-robots       # пусто!
```

Последняя строка важна: заголовок `X-Robots-Tag` на боевом домене появляться
не должен. Если он там есть — сервер отдаёт имя хоста не так, как ожидает
правило в `.htaccess`, и правило надо убрать, иначе сайт выпадет из поиска.

Затем:

- Google Search Console: добавить `/sitemap.xml`, старые карты уводят на неё сами;
- проверить несколько страниц инструментом проверки URL — должны быть `canonical`
  на себя и `hreflang` на три языка;
- через неделю посмотреть отчёт «Страницы»: ошибок 404 быть не должно.

## Что ещё не готово

Это не мешает переносу, но лучше знать до него:

- **Форма заявки демонстрационная.** Сейчас она показывает сообщение и никуда
  не отправляет. До переключения нужен обработчик: письмо на `info@mguliyev.com`
  и защита от спама.
- **Текст страниц пока только на русском.** Интерфейс, мета-теги, каталог услуг
  и 48 описаний проектов переведены на все три языка; текст самих страниц
  показывается по откату на русский. Это видно на `/en/portfolio/`.
- **Три статьи блога только на русском**, и сайт говорит об этом честно.
- **Пометки `[УТОЧНИТЬ]`** на страницах цен и контактов: WhatsApp, адрес офиса,
  цены продления и продвижения, способы оплаты, ссылки на соцсети,
  политика конфиденциальности.
- **Старый сайт останется на диске.** Когда убедитесь, что новый работает,
  его файлы и базу можно убрать — но не в день переключения.
